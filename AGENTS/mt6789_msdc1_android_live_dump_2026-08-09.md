# MT6789 MSDC1 — ЖИВОЙ ДАМП ANDROID (эталон рабочего состояния) — 2026-08-09

**Как снято:** стоковый LK прошит пользователем → Android 12 загрузился → adb (KernelSU root).
/dev/mem РАБОТАЕТ (вопреки опасениям), но MSDC1 читается как 0x0, пока контроллер в runtime
suspend. Разбудить: `dd if=/dev/block/mmcblk0 of=/dev/null bs=4096 count=65536 & sleep 0.02`
(длительная передача), ПАРАЛЛЕЛЬНО devmem-циклом снять регистры. После окончания передачи
контроллер мгновенно засыпает (все регистры = 0).

**Состояние карты:** mmc0 = 11240000.mmc (SD), тип SD, SS32G (Samsung 32GB), mmcblk0.
ios: clock=50000000, actual=47999984 (192МГц/4), timing=7 (UHS DDR50), voltage=1 (1.8V),
bus width=4bit. DT: mmc@11230000 (eMMC)=disabled, mmc@11240000 (SD)=okay.
debugfs смонтирован: mount -t debugfs debugfs /sys/kernel/debug.

## Гипотезы из дампа

1. **0x68 (MSDC_NEW_RX_CFG) = 0x54 в Android vs 0x36 у нас** — вероятно, остатки от
   BL2/LK (аппаратный дефолт?) или вендорская установка. 0x36≠0x54 — надо понять, кто
   ставит 0x54 (вендорский код? tune? autok?).
2. **0xb0/b4/b8 ≠ ни наши, ни вендорские init_hw-значения (0x403c0046/0xffff4089/...)** —
   видимо, вендор позже (после init_hw) меняет PATCH_BIT (в т.ч. биты из дампа:
   PATCH_BIT2 bit29=1 = CRCSTSENSEL?).
3. **TOP bit15 (ENH_EN) = 1 в Android** — мы пробовали консолью (0x11ef0000=0x8000) — не
   помогло, но это было в связке с нашими PATCH_BIT. Возможно, ENH_EN требует
   правильного PATCH_BIT2 (CFGCRCSTS etc).
4. **0x204 = 0x2D000000** — не интерпретировано; что пишет в 0x204?
5. 0x228 SDC_FIFO_CFG = 0 в Android — у нас 0x040C0080 (биты 7,18,19,26).

## ВЫВОДЫ из живого дампа

1. PATCH_BIT0=0x403C0007 — Android ЖИВЬЁМ РАВНО нашему LK-финалу (v213)! → v213 PATCH_BIT0
   корректен.
2. 0x228=0x040C0080 — совпадает. Наш SDC_FIFO_CFG корректен.
3. Различия-кандидаты: PATCH_BIT1 (0xFFFE4x4x), PATCH_BIT2 (0x348x180F), SDC_CFG
   (bits 20,27), 0x204 (bits 24,26,27,28), 0x64 (доп. биты), TOP bit15 (ENH_EN=1).
4. 0x204 = 0x2D000000 стабильно — похоже на КОНФИГ (не статус), у нас 0. Что это за
   регистр и кто его пишет — см. вендорский код.
5. PATCH_BIT1: 0xFFFE0000-часть (bits 17-23) НЕ совпадает ни с вендорским init_hw
   (0xffff4089 — биты 16-23), ни с LK (0xffe64309). Это странно — возможно, вендор
   меняет PATCH_BIT1 при переключении 1.8V/tuning.

## Итоговый анализ (сверка с вендорским кодом)

1. **CONFIG_MMC_AUTOK=m** — ядро использует AUTOK-ветку init_hw (mtk-mmc.c:1535-1549):
   НЕ пишет PATCH_BIT0/1 (остаются как LK оставил при загрузке!), только enhance_rx →
   TOP |= ENH_EN (bit15), support_64g → PATCH_BIT2 bit1.
2. **Живой PATCH_BIT0 = 0x403C0007 = LK-финал** — подтверждение, что на init-фазе
   PATCH_BIT0/1/2 = LK-значения (как наш v213!): LK ставит их при загрузке ядра.
3. **PATCH_BIT1 живой (0xFFFE4340) = LK (0xFFE64309) + авток-дельты**: +биты 19,20
   (0x180000), +бит6 (GET_BUSY_MA), −биты 0,3 (CMDTA/WRDAT) — это авток для DDR50
   (mtk-mmc-autok.c:2542-2551: GET_BUSY_MA=1, 0x3<<19, STOP_DLY=3, POPENCNT=8).
4. **PATCH_BIT2 живой (0x3488180F) = LK (0x14881805) + авток**: +бит29 (CRCSTSENSEL=1),
   +бит1 (SUPPORT_64G — ставит и init_hw!), +бит3, RESPSTSENSEL=1, POPENCNT=8,
   DDR50SEL=1 (бит19), биты 16/17 волатильны (авток крутит).
5. **Вывод: на init-фазе (400кГц) Android = LK-значения PATCH_BIT — КАК У НАС в v213.
   CRC-причина НЕ в PATCH_BIT!**
6. **Стабильные отличия живого Android vs наш v213, которые НЕ объясняются автоком:**
   | Рег | Android | v213 | |
   |---|---|---|---|
   | 0x64 ADV_CFG0 | 0x3808C169 (биты 0,3,6,7,8=1) | 0x3808E000 (бит13=1, биты 0,3,6,7,8=0) | НЕ ПРОВЕРЕНО |
   | 0x204 EMMC51_CFG0 | 0x2D000000 (биты 24,26,27,28) | 0 | НЕ ПРОВЕРЕНО |
   | TOP 0x11ef0000 | 0xA000 (ENH_EN+bit13) | 0 (v213 обнуляет!) | НЕ ПРОВЕРЕНО с LK-PATCH_BIT |
   | SDC_CFG | биты 19,20,24,27 | 19,24,25 | семантика бит 20/24/25/27 неясна |
7. TOP ENH_EN консолью пробовали ТОЛЬКО с вендорскими PATCH_BIT
   (0x403c0446/0xffff4309/0x1000000e) — с LK-PATCH_BIT не пробовали!
