# MT6789 MSDC1 — контроллер сам тянет CMD/DAT вниз (2026-08-08, продолжение CRC-расследования)

## КЛЮЧЕВОЕ ОТКРЫТИЕ СЕССИИ

**PS (0x11240008) показывает CMD и DAT1-3 в 0 (низкий уровень) при настроенных подтяжках.**
При этом **подтяжки РАБОТАЮТ** — доказано экспериментом:

| Режим GPIO72 (CMD) | PS (0x11240008) | Трактовка |
|---|---|---|
| mode=1 (MSDC1_CMD) | 0x00000002 | CMD(bit24)=0, DAT0(bit16)=0, CDSTS(bit1)=1 |
| mode=0 (GPIO) | **0x01000002** | **CMD(bit24)=1 — подтянулся!** |
| mode=1 обратно | 0x00000002 | CMD=0 |

→ Подтяжки (iocfg_rt, GPIO71-76) исправны. **В режиме MSDC1 сам контроллер драйвит
линии вниз** (или держит их в 0). Это НЕ похоже на рабочий Android: там карта
работает, значит CMD idle = 1 (иначе SD-команды невозможны).

Эксперимент проводился БЕЗ карты (вынута пользователем): без карты PS=0x00000002
(все линии 0). С картой было 0x00010002 (DAT0=1 — карта держит DAT0 высоко).

## Что проверено и ОТКЛОНЕНО в этой сессии

1. **VIO18 (LDO 1.8V IO, PMIC MT6359P адрес 0x1CAC)**: в Android-дампе
   `0x1cac = 0x0000` — ВЫКЛЮЧЕН и в Android! → не причина подтяжек.
   (regulator_summary говорит vio18=1800mV enabled=1 — противоречие с дампом;
   похоже, vio18 управляется другим битом/всегда-on, но факт: 0x1cac=0 у Android)
2. **SDIO-бит (sdc_cfg 0x30 bit19, 0x80000)**: снят (sdc_cfg=0x03000000) → PS без
   изменений (0x00000002). Не тянет линии вниз.
3. **CFGRESP (patch_bit2 bit15 = 0x8000, mw.l 0xb8 0x1000800e)**: установлен,
   rescan → лог прежний: CMD8/55 events=0x480 (RSPCRCERR). НЕ помог.
4. **RSPL (iocon bit1, mw.l 0x04 2)**: НЕВАЛИДЕН через консоль — драйвер
   перезаписывает iocon в set_mclk (пишет def_tune_para.iocon=0) и в reset_hw.
   Только правка кода (def_tune_para.iocon=2 в init_hw).
5. **sdc_resp[0..3] (0x40-0x4c) после CMD8-ошибки**: ВСЕ 0 — при CRC-ошибке
   контроллер не захватывает ответ; шину через регистры не увидеть.
6. **DRV (drive-strength, iocfg_rt 0x11EA0030)**: был 0x01249240 (поля=1), по dts
   должно быть 3; записал 0x06DB6C00 (все поля=3). PS не изменился.

## Подтверждённые факты (регистры/раскладки)

- **INT (0x1124000C) = 0x480 = RSPCRCERR(BIT10) + SDIOIRQ(BIT7)** — раскладка из
  GKI mtk-sd.c:146-149 и вендорного mtk-mmc.h (bit7=SDIOIRQ, bit10=RSPCRCERR).
  SDIOIRQ при DAT1=0 (низкий уровень) — ожидаемо (см. обработку в GKI:1086:
  SDIOIRQ проверяет PS_DATA1).
- **INTEN (0x11240010) = 0xd700** — это НЕ мусор, а наша маска
  CMD_INTS_MASK|DATA_INTS_MASK (0x700|0xd000). Регистры: CFG=0x00, IOCON=0x04,
  PS=0x08, INT=0x0C, INTEN=0x10, FIFOCS=0x14, SDC_CFG=0x30, SDC_CMD=0x34,
  SDC_ARG=0x38, SDC_STS=0x3C, SDC_RESP=0x40-0x4C, SDC_BLK_NUM=0x50.
  ВНИМАНИЕ: PS=0x11240008 (НЕ 0x4c!); INT=0x0c (НЕ 0x10!). В прошлых сессиях
  регистры могли читаться со сдвигом.
- **PS раскладка (GKI mtk-sd.c:130-137)**: CDEN=bit0, CDSTS=bit1, CDDEBOUNCE=12-15,
  DAT0-7=bit16-23, CMD=bit24, WP=bit31.
- **SDC_FIFO_CFG (0x11240228) = 0x040C0000**: bit24(WRVALIDSEL)=0, bit25(RDVALIDSEL)=0
  (LK их стирает — у нас уже 0 ✓), bit26=1 (0x04000000, назначение не ясно,
  LK не трогает). Проверить вендора: mtk-mmc.h: SDC_FIFO_CFG_WRVALIDSEL/RDVALIDSEL.

## pinctrl (подтверждено вендорным pinctrl-mt6789.c + cust_mt6789_msdc.dtsi)

GPIO 71-76 (MSDC1: 71=CLK, 72=CMD, 73-76=DAT0-3) живут в **iocfg_rt (0x11EA0000)**:
- IES (вход): 0x11EA0080, биты 1-6 (мы ставим 0x7E; сейчас 0x7F — бит0 лишний)
- SMT: 0x11EA0140, биты 16-21
- PUPD (1=up): 0x11EA00B0, биты 0-5 = 0x3F (нам: все up)
- R0 (24K): 0x11EA00E0, биты 0-5 = 0x3F
- R1 (4K): 0x11EA00F0, биты 0-5 = 0x00
- DRV (сила драйвера, 3 бита/пин): 0x11EA0030, поля: GPIO71=[11:9], 72=[14:12],
  73=[17:15], 74=[20:18], 75=[23:21], 76=[26:24]. Значение 3 → 0x06DB6C00
- Mode-регистры: GPIO71: 0x10005380 [31:28]=1; GPIO72-76: 0x10005390 = 0x11111 ✓
  (совпадает с PINMUX_GPIO7X__FUNC_MSDC1_* = функция 1)

**Вендорный cust_mt6789_msdc.dtsi (эталон)**:
- CMD/DAT0-3: input-enable, drive-strength=3, **bias-pull-up = MTK_PUPD_SET_R1R0_01**
  (R1=0, R0=1 → 24K)
- CLK: drive-strength=3, **bias-pull-down = MTK_PUPD_SET_R1R0_10** (R1=1, R0=0 → 4K)
  ← у нас CLK стоит pull-UP (PUPD бит0=1) — НЕПРАВИЛЬНО по вендору (но CLK в PS
  не читается, влияние на CRC неясно)
- pinctrl-names: "default", "state_uhs", "pull_down" (3 состояния, те же подтяжки)
- vmmc = mt6358_vmch_reg (2.9V), vqmmc = mt6358_vmc_reg (1.8V)
- cd-gpios = GPIO 7; host-index=1; no-mmc; no-sdio

Android-дамп pins.txt (для сверки): pin71: `1000031110 (1 0)` (CLK: R1=1,R0=0 → down),
pin72-76: `1001031111 (0 1)` (CMD/DAT: R1=0,R0=1 → up 24K) — совпадает с dts.

## pwrap-чтение из консоли U-Boot (рабочий рецепт)

```bash
mw.l 0x10001080 3          # включить pwrap-клоки (IFRAO0 pmic_tmr/pmic_ap)
mw.l 0x10026880 <addr>     # WACS2_CMD: команда чтения
sleep 1                    # !!! обязательная задержка (в коде udelay(200))
md.l 0x10026894 1          # SWINF_2_RDATA (НЕ WACS2_RDATA 0x8A8!)
```
ВАЖНО: первый read после включения может вернуть предыдущую транзакцию
(shift-by-1) — читать дважды. VLDCLR (0x100268A4)=1 между операциями.
PMIC MT6359P: LDO_VIO18_CON0 = 0x1CAC (EN=bit0; у Android = 0x0000).

## Состояние консоли U-Boot (полезно)

- Длинные цепочки команд (sleep+md) забивают очередь консоли; uart_cmd с малым
  таймаутом ловит хвост старых выводов (md.l по адресам 0x100268XX: 0x2844d —
  это НЕ мусор железа, а задержанный вывод старых команд).
- Лечится Ctrl+C: `python3 -c "import serial; s=serial.Serial('/dev/ttyACM0',115200);
  s.write(b'\x03\x03'); s.close()"` → чистый промпт `=> `.
- read_early_log.py читает буфер через md.b чанками по 256 Б (каждый = новый
  сеанс uart_cmd) → при большом буфере (13-30КБ) занимает минуты. Быстрее:
  /tmp/opencode/read_early_log_fast.py (чанк 1024) или ручной md.b 0x43fff010 0x3400.

## Выводы и направления

- Корневая проблема: **MSDC1-контроллер держит CMD/DAT1-3 в 0** (а должен idle=1).
  Вендорные PATCH_BIT/ENH_RX/CFGCRCSTS уже проверены — не влияют на 0x480.
- Следующие шаги:
  a) Сравнить полный снимок регистров MSDC1 с вендорским init (mtk-mmc.c:1450-1565):
     какие регистры вендор НЕ трогает/обнуляет, а у нас мусор (кандидаты: SDC_FIFO_CFG,
     TOP_CONTROL остальные биты, EMMC50_CFG0/1, DDLSEL, 0x228+).
  b) RSPL/другие iocon-биты — только через код (def_tune_para.iocon) + пересборку.
  c) Проверить, что в вендоре драйвит линии вверх: возможно, бит "OUTPUT-режим"
     или отсутствующий у нас шаг (например, PIO-режим/авто-такты).
