# MT6789 MSDC1 — диагностика живого устройства через uart_cmd.py

**Дата:** 2026-08-06 08:14 UTC  
**Метод:** чтение регистров через U-Boot shell (`md.l`) via `/dev/ttyACM0`  
**Инструмент:** `uart_cmd.py` — отправка команд в U-Boot через USB CDC ACM

## Команда uart_cmd.py

```bash
python3 uart_cmd.py [-p /dev/ttyACM0] [-b 115200] [-t 2.0] "cmd1" "cmd2" ...
```

**Параметры:**
- `-p` — порт (по умолчанию `/dev/ttyACM0`)
- `-b` — baud rate (по умолчанию 115200)
- `-t` — timeout в секундах (ожидание тишины после команды)
- Можно передавать несколько команд последовательно

**Особенности:**
- Автоматически сбрасывает input buffer
- Разбуживает приглашение (`\r\n`)
- Ждёт тишины перед отправкой команд
- Порт всегда закрывается (with-блок)

## Результаты чтения регистров

### 1. CLK_CFG_7 (0x10000080) — мультиплексор msdc30_1_sel

```
0x10000080: 0x01000401
```

**Декодирование:**
```
   3         2         1         0
  1098 7654 3210 9876 5432 1098 7654 3210
  0000 0001 0000 0000 0000 0100 0000 0001
  
  [31:26] = 0x00
  [25:24] = 0x01  → другой мультиплексор (возможно, msdc5hclk_sel?)
  [23:16] = 0x00
  [15]    = 0     → gate OFF (клок включён) ✓
  [14:11] = 0
  [10:8]  = 0x4   → **индекс родителя = 4 = msdcpll_d2** ⚠️
  [7:3]   = 0
  [2:0]   = 0x1   → msdc50_0_sel (другой мультиплексор)
```

**Вывод:** LK выбрал **`msdcpll_d2`** (индекс 4), а не `tck_26m_mx9_ck` (индекс 0)!

По таблице из `clk-mt6789-topckgen.c:323-329`:
```c
static const char * const msdc30_1_parents[] = {
    "tck_26m_mx9_ck",      // [0] 26 MHz
    "univpll_d6_d2",       // [1] ~167 MHz
    "mainpll_d6_d2",       // [2] ~137 MHz
    "mainpll_d7_d2",       // [3] ~118 MHz
    "msdcpll_d2"           // [4] ← ВЫБРАН
};
```

### 2. MSDCPLL (0x1000C350-0x1000C35C)

```
CON0 (0x350): 0x000003e1
CON1 (0x354): 0x031d89d8
CON2 (0x35C): 0x001d89d8
CON3 (0x360): 0x80000001
```

**Декодирование CON0:**
```
[31:27] = 0
[26:24] = 0 (POSDIV = 0 → делитель 1)
[23:0]  = 0x3e1
```

**Декодирование CON1:**
```
[31:22] = 0x00c (биты старшие)
[21:0]  = 0x1d89d8 (PCW = 1935832)
```

**Декодирование CON2:**
```
[31:1] = 0x00eca4e (биты конфигурации)
[0]    = 0  → **PLL DISABLED** ⚠️⚠️⚠️
```

**Формула частоты (если бы PLL был включён):**
```
f_pll = 26 MHz * (PCW / 2^22) / (2^POSDIV)
      = 26 MHz * (1935832 / 4194304) / 1
      = 26 MHz * 0.4616
      = 12.0 MHz
```

**⚠️ КРИТИЧНАЯ ПРОБЛЕМА:** MSDCPLL выключен (CON2[0] = 0), но мультиплексор выбрал `msdcpll_d2` как источник!

**Возможные объяснения:**
1. **Bypass mode:** когда PLL выключен, `msdcpll_d2` работает как pass-through от `clk26m` (26 MHz)
2. **Ошибка конфигурации:** LK забыл включить PLL, но мультиплексор указывает на него
3. **Другой источник:** `msdcpll_d2` берёт частоту из другого PLL через внутренний мультиплексор

### 3. CLK_CFG_6 (0x10000070) — msdc5hclk_sel

```
0x10000070: 0x01040001
```

**Декодирование:**

```
[31]    = 0     → gate OFF (клок включён)
[25:24] = 0x1   → индекс родителя = 1 = mainpll_d4_d2 (~206 MHz)
[7:0]   = 0x01
```

**Вывод:** HCLK настроен на ~206 MHz — это нормально для высокоскоростной шины.

### 4. CLK_CFG_UPDATE (0x10000004)

```
0x10000014: 0x03000202
```

Все биты update = 0 → конфигурация мультиплексоров зафиксирована.

### 5. MSDC1 контроллер (0x11240000)

```
+0x00: 0x02000099  MSDC_CFG
+0x04: 0x00000000  MSDC_IOCON
+0x08: 0x00000002
+0x0C: 0x00000080  MSDC_INTEN?
+0x10: 0x0000d700
+0x30: 0x03080000  SDC_CFG
+0x70: 0x00000000  PATCH_BIT0
+0xB0: 0x403c0046  PAD_TUNE0
+0xB4: 0xffff4309  PAD_TUNE1
+0xB8: 0x448a180f  ???
```

**MSDC_CFG (0x02000099):**
```
[31:26] = 0
[25]    = 1  → какой-то флаг
[24:4]  = 0
[3:0]   = 0x9 (1001) → биты [3]=RST?, [2]=?, [1]=?, [0]=?
```

**PAD_TUNE0 (0x403c0046):**
- LK записывает `0x403c0007`
- Устройство показывает `0x403c0046`
- Разница: биты [6:0] = `0x46` вместо `0x07`

**PAD_TUNE1 (0xffff4309):**
- LK записывает `0xffe64309`
- Устройство показывает `0xffff4309`
- Разница: биты [23:16] = `0xff` вместо `0xe6`

**Гипотеза:** U-Boot или LK перенастроили таймиги после инициализации.

### 6. GPIO pull control (0x10C00C28)

```
0x10C00C28: 0x00000000
```

Для MSDC1 GPIO 0xa7:
- Регистр: `0x10C00C00 + (0xa7 >> 4)*4 = 0x10C00C00 + 0x28`
- Бит: `(0xa7 & 0xf) << 1 = 7 << 1 = 14`

**Значение бита 14 = 0** → pull **enabled** (согласно LK логике: `param_2 != 0` → сброс бита).

### 7. Pin config (0x11D40090)

```
0x11D40090: 0x00000000
0x11D400A0: 0x00000000
```

**⚠️ КРИТИЧНО:** Все биты = 0, но LK должен был установить:
```c
// FUN_ffff000050f43ae0, строки 51263, 51277-51278 для MSDC1:
_DAT_ffff000011d40090 |= 0x01;   // бит 0
_DAT_ffff000011d400c0 |= 0x3f;   // биты [5:0]
_DAT_ffff000011d400b0 &= ~0x3f;  // сброс [5:0]
```

**Гипотеза:** U-Boot сбросил конфигурацию пинов, либо адреса неправильные.

## Корневая причина проблемы

### Найдена: source clock = bypass 26 MHz через выключенный MSDCPLL

**Цепочка:**
1. Мультиплексор `msdc30_1_sel` выбрал индекс 4 (`msdcpll_d2`)
2. MSDCPLL выключен (CON2[0] = 0)
3. В bypass mode `msdcpll_d2` = `clk26m / 2` = **13 MHz** (?)
   - Или pass-through: `msdcpll_d2` = `clk26m` = **26 MHz**

**Проверка гипотезы:**

Если source clock = 13 MHz:
- Делитель для 400 kHz: `13000 / 400 = 32.5` ✓ (округляется до 32 или 33)
- Делитель для 100 kHz: `13000 / 100 = 130` ✓

Если source clock = 26 MHz:
- Делитель для 400 kHz: `26000 / 400 = 65`
- Делитель для 100 kHz: `26000 / 100 = 260`

**Драйвер U-Boot (`drivers/mmc/mtk-sd.c`):**
- Вероятно, программирует делитель для source clock = 200 MHz (как для других MTK SoC)
- Реальный source = 13 или 26 MHz
- **Результат:** частота на SD-шине в 8-15 раз ниже, чем должна быть
- Карта не успевает ответить из-за слишком низкой частоты? Или наоборот?

### Дополнительная проблема: пины не настроены

Регистры `0x11D40090` = 0 → пины в дефолтном состоянии, не в режиме MSDC1.

## План исправления

### 1. Явно включить MSDCPLL в U-Boot (если нужен)

```c
// В drivers/clk/mediatek/clk-mt6789.c или board init:
writel(0x000003e1, 0x1000C350);  // CON0: POSDIV=0
writel(0x031d89d8, 0x1000C354);  // CON1: PCW
writel(0x001d89d9, 0x1000C35C);  // CON2: enable (бит 0 = 1)
udelay(20);  // ожидание стабилизации PLL
```

### 2. Переключить msdc30_1_sel на 26 MHz (индекс 0)

```c
// В drivers/mmc/mtk-sd.c, перед msdc_init():
writel(0x00000700, 0x10000084);  // CLR: сбросить биты [10:8]
writel(0x00000000, 0x10000080);  // SET: индекс 0 (tck_26m)
writel(0x20000000, 0x1000008C);  // UPDATE: strobe бит 29
udelay(1);
```

### 3. Настроить пины MSDC1

```c
// Настройка режима пинов (0x11D40090):
u32 val = readl(0x11D40090);
val |= 0x01;  // включить бит 0
writel(val, 0x11D40090);

// Настройка pull-up/down (0x11D400C0):
val = readl(0x11D400C0);
val |= 0x3f;  // биты [5:0]
writel(val, 0x11D400C0);

// Сброс (0x11D400B0):
val = readl(0x11D400B0);
val &= ~0x3f;
writel(val, 0x11D400B0);
```

### 4. Проверить делитель в драйвере

В `mtk-sd.c`, функция `msdc_set_mclk()`:
```c
// Убедиться, что source clock = 26 MHz:
unsigned long src_clk = 26000000;  // явно, не из clk framework
// Затем вычислить делитель
```

## Выводы

1. **Source clock:** LK выбрал `msdcpll_d2`, но MSDCPLL выключен → bypass mode (13 или 26 MHz)
2. **Драйвер U-Boot:** вероятно, ожидает 200 MHz и программирует неправильный делитель
3. **Пины не настроены:** регистры 0x11D40090 = 0 (должно быть 0x01)
4. **Решение:** явно установить source clock на 26 MHz (индекс 0) и настроить пины

## Эксперименты с runtime переключением клока (2026-08-06 08:18 UTC)

### Попытка 1: SET/CLR/UPD последовательность (индекс 0)
```bash

```

### Попытка 2: SET/CLR/UPD последовательность (индекс 3)
```bash

```
**Результат:** `0x10000080 = 0x01000701` (опять индекс 7!)

### Попытка 3: Прямая запись полного значения
```bash

```
**Результат:** `0x10000080 = 0x01000701` (не изменилось)

### Попытка 4: Только SET без CLR
```bash

mw.l 0x1000008C 0x20000000  # UPDATE
```
**Результат:** `0x10000080 = 0x01000701` (не изменилось)

### Вывод
**CLK_CFG_7 защищён от записи в runtime** — все попытки изменить биты [10:8] проваливаются. Возможные причины:
1. Защита от записи на уровне hardware (secure world)
2. Требуется специальная unlock-последовательность (не документирована)
3. Регистр можно изменить только на ранних стадиях загрузки (BL2/LK)

**Проблема с CLR регистром:** запись `0x700` в `0x10000084` не сбрасывает биты [10:8], а **устанавливает их все в 1** (индекс 7). Это противоречит логике kernel driver, где CLR должен сбрасывать биты.

**Гипотеза:** MT6789 использует другую схему SET/CLR регистров, либо topckgen заблокирован после LK.
