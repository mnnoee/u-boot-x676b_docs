# MT6789 MSDC1 — сессия 2026-08-08/09: полный дамп регистров, эксперименты A-G (2026-08-09)

**Статус:** SD-карта не инициализируется, CMD8/CMD55 = RSPCRCERR (0x480). Эксперименты A-G
не изменили CRC. Доказано: линии, подтяжки и питание карты ИСПРАВНЫ. Карта 100% рабочая
(Android на этом же устройстве с ней корректно общается). pwrap умер во время сессии.

## Железо/среда
- U-Boot v191 (собран 2026-08-08 13:02, git f3abb346964), карта ВСТАВЛЕНА (подтвердил пользователь)
- Консоль: /dev/ttyACM0 (921600), MCP serial

## 1. Полный дамп MSDC1 (0x11240000) — 2026-08-08, после загрузки и mmc dev 0

```
0x00 MSDC_CFG     = 0x0200789b  (после set_mclk 400кГц: div=120, MODE, PIO, CKSTB; bit25)
0x04 MSDC_IOCON   = 0x00000000  (RSPL=0, DSPL=0, DDLSEL=0)
0x08 MSDC_PS      = 0x00010002  (CDSTS=1, DAT0=1, CMD=0)
0x0c MSDC_INT     = 0x00000480  (RSPCRCERR(bit10) + SDIOIRQ(bit7))
0x10 MSDC_INTEN   = 0x0000d700  (CMD_INTS_MASK|DATA_INTS_MASK)
0x14 MSDC_FIFOCS  = 0x00000000
0x30 SDC_CFG      = 0x03080000  (DTOC=3, SDIO(bit19)=1, BUSWIDTH=0)
0x34 SDC_CMD      = 0x00000000  (после reset_hw)
0x38 SDC_ARG      = 0x00000000
0x3c SDC_STS      = 0x00000000
0x40-0x4c SDC_RESP = 0 (CRC-ошибка → ответ не захватывается)
0x50 SDC_BLK_NUM  = 0
0x54              = 0x00000145 (в первом дампе; потом 0)
0x64 SDC_ADV_CFG0 = 0x3808e000  (← НЕ мусор; менялся между чтениями: 0x3808c000 → 0x3808e000!)
0x68 EMMC_CFG0    = 0x00000036
0x6c..0x8c        = 0
0x90..0x94        = 0
0x98              = 0x00006008  (стабильно; sw_dbg_out?)
0x9c              = 0x00000004  (стабильно)
0xa8              = 0x20210706  (main_ver/eco_ver: "21.07.06" — версия IP контроллера)
0xb0 PATCH_BIT0   = 0x403c0046  (наш init_hw: БЕЗ CKGEN_MSDC_DLY_SEL=1; вендор: 0x403c0446!)
0xb4 PATCH_BIT1   = 0xffff4309  (наш: 0xffff4089 + STOP_DLY=3; вендор так же)
0xb8 PATCH_BIT2   = 0x448a180f  (наш: RESPWAIT=3, RESPSTSENSEL=2, CRCSTSENSEL=2, CFGCRCSTS=0;
                                вендор: ENH_RX + CFGCRCSTS=1 + SUPPORT_64G → 0x1000000e)
0xf0 PAD_TUNE0    = 0x00000007  (← МУСОР от хака: writel(0x403c0007) в pad_tune0, write-mask
                                пропускает только младшие биты! LK обнуляет PAD_TUNE0/1)
0xf4 PAD_TUNE1    = 0x00000000
0x118             = 0x20210706
0x228 SDC_FIFO_CFG = 0x040c0080  (WRVALIDSEL=0, RDVALIDSEL=0 ✓; биты 7,18,19,26; в прошлой
                                 сессии было 0x040c0000 — бит 7 добавился сам/другим кодом)
0x11ef0000 TOP_CONTROL = 0x00002000 (bit13 PAD_DAT_RD_RXDLY_SEL ✓; ENH_EN bit15 = 0!)
0x11ef0004 TOP_CMD     = 0x00000800 (bit11 PAD_CMD_RD_RXDLY_SEL ✓)
```

ВНИМАНИЕ: значения 0x98/0x9c/0x64 (0x6008, 0x4, 0x3808e000) — стабильные/меняющиеся
неизвестные регистры. Не интерпретированы. 0x64 менялся между чтениями (0x3808c000→0x3808e000) —
возможно, живой статус/DMA-остатки LK.

## 2. PWRAP умер во время сессии — ВАЖНО для следующих сессий

Последовательность, после которой pwrap сдох (все регистры 0x10026000-0x100268A8 стали 0x400):
1. Успешные чтения: CMD=0x1E48 → RDATA=0x200 ✓; CMD=0x1E4C → RDATA=0x400 ✓ (VLDCLR после каждого)
2. Потом цепочка (mw.l CMD 0x1CD8; sleep; md RDATA; mw VLDCLR; mw CMD 0x1CC4; sleep; md; mw VLDCLR)
   — порт MCP закрылся, вывод потерян
3. После этого ВСЕ чтения pwrap возвращают 0x400, включая INIT_DONE2 (был 1) и WACS2_RDATA (был 0x8441)

ВЫВОДЫ:
- Причина смерти: запись CMD в WACS2 в момент, когда предыдущая транзакция не завершена/
  без VLDCLR (цепочка). Правило: **CMD → пауза ≥200µs → RDATA → VLDCLR → пауза → следующая CMD.**
  Нельзя писать CMD, пока VALID не сброшен.
- "0x400 во всех регистрах pwrap" = новый паттерн смерти (прошлый раз был "все 0x0").
- Восстановление: только холодная перезагрузка.
- Т.к. pwrap умер ПОСЛЕ чтения VMCH/VMC=включено, питание SD осталось (PMIC не сбрасывается).

## 3. ДОКАЗАНО: подтяжки, линии и питание карты ИСПРАВНЫ

Эксперимент с GPIO-модами (безопасный, без перезагрузки):
```
GPIO72 (CMD) mode 1 (MSDC): PS=0x00000002 (CMD=0 — контроллер держит вниз)
GPIO72 (CMD) mode 0 (GPIO): PS=0x01000002 (CMD=1 — подтянулся! → питание+подтяжка есть)
GPIO73 (DAT0) mode 0 (GPIO): PS=0x00010002 (DAT0=1 — карта тянет вверх → КАРТА ЗАПИТАНА!)
```
→ Линии, подтяжки, питание карты в порядке. В MSDC-режиме контроллер сам драйвит
CMD/DAT0 вниз (idle должен быть 1). После RST (MSDC_CFG bit2) контроллер отпускает
линии (PS снова 0x10002).

Замечание: 0x10005390 = 0x11111111 (8 нибблов mode 1, не 0x11111 как в старом доке —
видимо, драйвер настроил и соседние пины, или раскладка иная; GPIO72=[3:0]).

## 4. Эксперимент A — PAD_TUNE0/1 обнуление (гипотеза: мусор 0x7 в PAD_TUNE0)

Команды:
```
mw.l 0x112400f0 0; mw.l 0x112400f4 0
mw.l 0x11240000 0x0200009D   (RST)
mmc dev 0
```
Результат: PAD_TUNE0=0 подтверждено чтением. INT по-прежнему 0x480 (RSPCRCERR).
PS=0x00010002 (DAT0=1, линии свободны). → **PAD_TUNE0=0x7 НЕ причина CRC.**

## 5. Эксперимент B — pinctrl по вендору (CLK pull-down, DRV=3)

Гипотеза: у нас CLK pull-up (PUPD=0x3F) вместо pull-down, DRV=1 вместо 3 (вендор: DRV=3,
CLK pull-down 4K, CMD/DAT pull-up 24K).

Команды:
```
mw.l 0x11EA00B0 0x3E          # PUPD: CLK(71)=0(down), CMD/DAT=1(up)
mw.l 0x11EA00E0 0x3E          # R0: CLK=0, CMD/DAT=1 (24K)
mw.l 0x11EA00F0 0x01          # R1: CLK=1 (4K down), CMD/DAT=0
mw.l 0x11EA0030 0x036DB600    # DRV: все поля GPIO71-76 = 3
                              # (в прошлой сессии писали 0x06DB6C00 — там GPIO73=2, ошибка!)
mw.l 0x11240000 0x0200789D    # RST
mmc dev 0
```
Результат: INT = 0x480 (RSPCRCERR), PS = 0x00010002. → **pinctrl (CLK PD, DRV=3) НЕ причина CRC.**

## 6. Эксперимент C — RSPL (iocon bit1) — НЕ ВЫПОЛНИМ через консоль

```
mw.l 0x11240004 2   # RSPL=1
mmc dev 0           # повторный
md.l 0x11240004 1   # → 0x00000000 !!
```
set_mclk перезаписывает iocon = def_tune_para.iocon (=0) даже при повторном mmc dev 0
(условие host->mclk != clock || host->timing != selected_mode срабатывает — timing меняется).
→ RSPL можно проверить ТОЛЬКО правкой кода: def_tune_para.iocon = MSDC_IOCON_RSPL в init_hw.
CRC после попытки = 0x480.

## 7. Эксперимент D — RSPL через DTS (r_smpl=1) — НЕ ПОМОГ (2026-08-09)

- Правка: `r_smpl = <1>;` в &sdhc2 (mt6789-infinix-x676b.dts). Драйвер: r_smpl → init_hw
  setbits RSPL (mtk-sd.c:1585). Билд v209, прошит пользователем.
- Результат: `mmc dev 0` молча fail, INT=0x480 (RSPCRCERR), PS=0x00010002.
- Early log подтверждает: CMD0 ok (0x180), CMD8/CMD55 → status=0x480, ровно как без RSPL.
- ВЫВОД: RSPL не влияет на CRC-ошибку. Закрытая гипотеза.

## 8. Эксперимент E — vendor pinctrl в коде (v210) — НЕ ПОМОГ (2026-08-09)

- Правка mtk-sd.c (probe, хендкод после pinctrl_select_state): было `PUPD |= 0x3F; R0 |= 0x3F;
  R1 &= ~0x3F` (все pull-up) — перебивало правильный DTS. Стало: PUPD=0x3E (CLK pull-down,
  CMD/DAT pull-up), R0=0x3E, R1=0x01, DRV=0x036DB600 + EARLY печать итоговых значений.
- Результат на железе: 0x11EA00B0=0x3E, 0x11EA00E0=0x3E, 0x11EA00F0=0x01, 0x11EA0030=0x036DB600
  — значения вендора ПОДТВЕРЖДЕНЫ. INT=0x480. → **pinctrl в КОДЕ не причина CRC** (совпало
  с экспериментом B консолью). Закрытая гипотеза.

## 9. Эксперимент F — SDC_DAT1_IRQ_TRIGGER (ADV_CFG0 bit24) — НЕ ПОМОГ (2026-08-09)

- Обнаружено при пошаговом сравнении init_hw: вендор ставит
  `sdr_set_bits(SDC_ADV_CFG0, SDC_DAT1_IRQ_TRIGGER)` (mtk-mmc.c:1591), у нас бит24=0.
- `mw.l 0x11240064 0x3908e000` (bit24=1), затем mmc dev 0.
- Результат: INT=0x480. 0x64 прочитался как 0x3908c000 (bit13 волатильный, bit24 остался=1 —
  запись реально прошла). → **DAT1_IRQ_TRIGGER не причина CRC.** Закрытая гипотеза.

## 10. Эксперимент G — полное выключение питания устройства — НЕ ПОМОГ (2026-08-09)

- Гипотеза: карта оставалась в UHS-состоянии от Android (перезагрузки не выключали питание
  слота; наш power_cycle в U-Boot не выключает питание карты — нет regulator-драйвера).
- Пользователь выключил устройство полностью, подождал, включил.
- Результат: INT=0x480. → **состояние карты при включении не причина CRC.** Закрытая гипотеза.
- Примечание: после перезагрузки консоль U-Boot оказалась на /dev/ttyACM1 (не ttyACM0!).

## 11. Полная сверка с вендорским драйвером (mtk-mmc.c) — ВСЁ СОВПАДАЕТ

Пошаговое сравнение (init_hw, set_mclk, probe, get_op_cond, msdc_start_command):
- init_hw: MODE, reset, INTEN=0/clear, internal_cd off, TOP=0/CMD=0, IOCON=0, PATCH_BIT0
  0x403c0046(+DLY_SEL), PATCH_BIT1 0xffff4089(+STOP_DLY=3), EMMC50_CFG0 CFCSTS_SEL,
  busy_check clr bit7, async_fifo RESPWAIT=3 + ENH_RX (top bit15) + CFGRESP=0 + CFGCRCSTS,
  SUPPORT_64G, data_tune (PAD_DAT_RD_RXDLY_SEL, DATA_K_VALUE_SEL clr, PAD_CMD_RD_RXDLY_SEL),
  SDC_CFG SDIO set/SDIOIDE clr, DTOC=3 — **все шаги вендора реализованы/проверены консолью**.
- Единственное несинхронизированное в коде (DAT1_IRQ_TRIGGER) — проверено консолью (F), не помогло.
- set_mclk: та же формула (div=120, sclk=400000), msdc_set_timeout вызывается ✓.
- Такты: src=192МГц (msdcpll_d2, как в Android), 400 кГц на линии (расчёт) ✓.
- Питание: VMCH=2.9V, VMC=1.8V — идентично Android (regulator_summary.txt) ✓.
- Pinctrl: CMD/DAT pull-up 24K, CLK pull-down 4K, DRV=3 — идентично Android DTS ✓.
- Вендорский DTS mmc1: НЕТ resets; cd-gpios ACTIVE_LOW (у нас в dts ACTIVE_HIGH — не влияет на CRC).
- 0x98=MSDC_DMA_CTRL, 0x9c=MSDC_DMA_CFG (DMA-регистры, не влияют на ответы).
- 0x68 (MSDC_NEW_RX_CFG)=0x36 — вендор для MT6789 не трогает (new_rx_ver=0).

## 12. Выводы (итог)

- CRC-ошибка ответа НЕ зависит от (проверено на железе): PAD_TUNE0/1, PATCH_BIT0/1/2
  (вендорные значения через консоль), pinctrl (mode/подтяжки/DRV — консолью и кодом),
  питания (доказано GPIO-модами; порядок включения — холодный старт), тактов
  (192 МГц = Android; 400 кГц расчёт), RSPL (кодом v209), DAT1_IRQ_TRIGGER (консолью),
  состояния карты (полное выключение питания).
- ФАКТ: карта ОТВЕЧАЕТ на CMD8/CMD55 (стартовый бит принят — RSPCRCERR, а не RSPTIMEOUT),
  но CRC ответа не сходится. CMD0 (без ответа) всегда ок.
- Вывод: программная инициализация контроллера максимально приближена к вендорской,
  расхождений, способных вызвать CRC, не найдено. Проблема либо в физическом сигнале
  (нечем измерить), либо в детали, которая не видна в статике регистров
  (динамика: переходные процессы, тактовая частота на линии на самом деле ≠ 400 кГц).
- 0x64: при 0x3908e000→чтение 0x3908c000: бит13 (0x2000) волатильный (ж/д статус?).
  SDC_FIFO_CFG bit7 (0x80) — назначение неизвестно, менялся между сессиями.

## 13. План (что дальше)

1. **Декомпилированный LK (lk_unpack_v0)** — ЕДИНСТВЕННЫЙ непроверенный первоисточник:
   полный разбор LK-инициализации MSDC1 (порядок шагов, регистры 0x98/0x9c/0x64,
   неизвестные биты, дебаунс). Найти расхождения с нашим init и проверить консолью.
2. Если LK ничем не отличается — **динамическое измерение тактов** через сам контроллер:
   MSDC_DBG_SEL/DBG_OUT (0xa0/0xa4) — внутренний mux сигналов, может показать CLK/CMD/DAT
   на линии без осциллографа (нужен мануал/сравнение с вендорским mtk-mmc-dbg.c).
3. **Тест с САМЫМ МЕДЛЕННЫМ делителем**: src=192МГц, попробовать 26 кГц-подобные значения
   (div=4095) — если CRC пройдёт на очень низкой частоте, проблема в реальной частоте на линии.
4. **Сравнить с GKI-ядром** (src_linux/gki-kernel/drivers/mmc/host/mtk-sd.c, mt6779_compat) —
   поиск отличий, которых нет ни у нас, ни в vendor (например, иной порядок CMD0 перед CMD8).
5. Как крайний вариант: **программный GPIO-приём ответа карты** (DAT0 в GPIO-режим,
   побитовая выборка через задержку в U-Boot-команде) — без железа, но трудоёмко.
