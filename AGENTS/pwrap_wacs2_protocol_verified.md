# PWRAP WACS2 протокол MT6789 — верифицирован + питание SD

**Дата:** 2026-08-06 · **Статус:** протокол подтверждён ядром и LK; на железе чтение 0xA (SWCID)
работает, 0x1CD8 (VMCH) пока не прочитан — причина установлена (незакрытая транзакция).

## Сводка

pwrap WACS2 на MT6789 (PWRAP_CAP_ARB) — рабочий канал к PMIC MT6366. Регистры базы 0x10026000.

| Регистр | Смещение | Абсолютный | Назначение |
|---|---|---|---|
| `PWRAP_INIT_DONE2` | 0x000 | 0x10026000 | признак инициализации канала |
| `PWRAP_WACS2_CMD` | 0x880 | 0x10026880 | команда |
| `PWRAP_SWINF_2_WDATA_31_0` | 0x884 | 0x10026884 | данные записи |
| `PWRAP_SWINF_2_RDATA_31_0` | 0x894 | 0x10026894 | данные чтения (мл. 16 бит) |
| `PWRAP_WACS2_VLDCLR` | 0x8A4 | 0x100268A4 | запись 1 = закрыть транзакцию |
| `PWRAP_WACS2_RDATA` | 0x8A8 | 0x100268A8 | статус FSM |

### FSM (регистр 0x100268A8)

`PWRAP_GET_WACS_ARB_FSM(x) = (x >> 1) & 7` (биты [3:1]):

| Значение | Состояние |
|---|---|
| 0 | IDLE |
| 2 | REQ |
| 4 | WFDLE |
| 6 | WFVLDCLR (данные готовы) |

`INIT_DONE1 = BIT(15)` в 0x100268A8 — канал инициализирован (на железе: 0x2844D, бит 15 = 1 ✓).
Для MT6789 регистра `WACS2_EN` НЕТ (это таблицы других SoC) — EN не нужен.

## Транзакция чтения (ядро pwrap_read16 и LK FUN_0004a334 — идентичны)

```
1. ждать FSM == IDLE (0);  при таймауте: если FSM==6 → записать 1 в VLDCLR (0x8A4)
2. CMD[0x10026880] = адрес & 0xffff        // для ARB адрес КАК ЕСТЬ, без сдвига (>>1 не нужен!)
3. ждать FSM == WFVLDCLR (6)
4. данные = readl(0x10026894) & 0xffff     // SWINF_2_RDATA
5. VLDCLR[0x100268A4] = 1                  // ОБЯЗАТЕЛЬНО после чтения
```

## Транзакция записи

```
1. ждать FSM == IDLE
2. WDATA[0x10026884] = данные & 0xffff
3. CMD[0x10026880] = BIT(29) | адрес       // 0x20000000 = признак записи
4. завершения не ждём, VLDCLR не пишем
```

## ⚠️ Главная грабля: незакрытая транзакция

Комментарий из ядра (mtk-pmic-wrap.c:1432-1439): если после чтения не записать VLDCLR,
FSM застревает в WFVLDCLR(6), и **следующая команда не стартует** — pwrap игнорирует CMD.

Именно это произошло на железе:
1. Прочитали 0xA → FSM остался в 6 (VLDCLR не писали)
2. Записали CMD=0x1CD8 при FSM≠IDLE → команда не принята
3. После записи VLDCLR FSM ушёл в 0 (IDLE), но данные в 0x894 остались старые (0x6610)

Симптом: статус 0x6610 → (>>1)&7 = 0 (IDLE), данные не обновились. Это «команда не стартовала»,
а НЕ «PMIC не ответил». Если бы PMIC молчал — был бы зависший FSM или мусор в данных.

## Готовая отладочная последовательность (с шелла U-Boot)

```
mw.l 0x100268A4 1          # сбросить залипшую транзакцию
md.l 0x100268A8 1          # ждать FSM=0 (биты [3:1])
mw.l 0x10026880 0x1CD8     # команда чтения
md.l 0x100268A8 1          # ждать (v>>1)&7 == 6
md.l 0x10026894 1          # данные
mw.l 0x100268A4 1          # закрыть транзакцию — ВСЕГДА!
```

Между любыми двумя чтениями обязателен VLDCLR (шаг 1 или последний шаг).

> Пакетная отправка строк в CDC-ACM теряет символы — слать по одной, либо через uart_cmd.py
> (но он шлёт быстро — добавить паузы между командами или по одному вызову на команду).

## Адреса регуляторов SD (MT6366, совместим с MT6358)

Проверено: SWCID (0xA) = 0x6610 → chip_id = 0x66 = MT6366. Адреса из
`include/linux/mfd/mt6358/registers.h` и `drivers/regulator/mt6358-regulator.c`:

| LDO | Роль | Enable (бит 0) | Напряжение (ANA_CON0) | Статус QI |
|---|---|---|---|---|
| **VMCH** | vmmc — VDD карты | 0x1CD8 | 0x1E48: [10:8]=2→2.9V, 3→3.0V, **5→3.3V** | 0x1CE6? |
| **VMC** | vqmmc — VccQ шины | 0x1CC4 | 0x1E4C: [11:8]=4→1.8V, 0xA→2.9V, 0xB→3.0V, **0xD→3.3V** | 0x1CD2? |

Для обычной SD: VMCH=3.3V (0x0500 в 0x1E48), VMC=3.3V (0x0D00 в 0x1E4C) — для UHS позже VMC 1.8V.

## Кто включает питание SD

- **LK не трогает** (в lk_a_lk.bin.c нет 0x1CD8/0x1CC4/vmch/vmc) — LK pwrap ходит только к ADC (0xD88), флагу батареи (0x152).
- Preloader — по косвенным признакам тоже не включает (питание SD включает ядро через mt6358-regulator.ko).
- Значит **в U-Boot питание VMCH/VMC надо включать самому** — это блокирующий шаг для SD.
