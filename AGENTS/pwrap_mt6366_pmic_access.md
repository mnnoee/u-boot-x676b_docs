# PWRAP / MT6366 — доступ к PMIC с MT6789

**Дата:** 2026-08-05 · **Прошивка на устройстве при замерах:** v188 (`g2937d2d3ce18`)
**Статус:** протокол подтверждён двумя независимыми источниками; доступ с железа **не получен**.

## Зачем это нужно

`mmc1` (MSDC1, SD-карта) в стоковом DT питается от PMIC:

```
mmc1: mmc@11240000 {
        vmmc-supply  = <0x85>;   → регулятор "vmch"   (VDD карты)
        vqmmc-supply = <0x86>;   → регулятор "vmc"    (VccQ, шина)
};
```

Оба LDO живут в **MT6366**, который висит на pwrap. Пока питание не подтверждено, диагностика
клоков MSDC1 и полярности card-detect не имеет смысла: карта не ответит на CMD0 просто потому,
что обесточена. Это делает pwrap блокирующим звеном для всей ветки SD.

## ⚠️ Две ошибки, из-за которых прошлое расследование дало ложный результат

Обе встречались в сессии агента до 2026-08-05. Если увидишь их в старых заметках — выводы оттуда
недействительны.

### 1. Склейка базы и смещения вместо сложения

```
mw.l 0x1002608a4 1          ← НЕВЕРНО: девять hex-цифр
mw.l 0x100260880 0x001cd800 ← НЕВЕРНО
```

`0x10026` + `08a4` было записано подряд, а не сложено. Получился адрес `0x1_002608A4` — за
пределами 4 ГБ, в неотображённой памяти. Правильно:

| Написано было | Правильно |
|---|---|
| `0x100260880` | `0x10026880` |
| `0x1002608a4` | `0x100268a4` |
| `0x1002608a8` | `0x100268a8` |
| `0x100260894` | `0x10026894` |

Симптомы этой ошибки: чтения возвращают `0xffffffff`, статус «не меняется», FSM «никогда не idle».
Отсюда родился неверный вывод «pwrap не работает».

### 2. `0x10000000` принят за infra_ao

`0x10000000` — это **topckgen**. `infra_ao` начинается с **`0x10001000`**.

Чтение `md.l 0x10000090` интерпретировалось как статус гейтов infra (`sta_ofs = 0x90`), но
фактически читался `CLK_CFG_8` из topckgen. Вывод «клок PMIC_TMR выключен» построен на постороннем
регистре и **неверен** (см. замеры ниже).

## Протокол WACS2 — подтверждён

База pwrap: **`0x10026000`** (`pwrap@10026000`, compatible `mediatek,mt6789-pwrap`).

Два независимых источника совпадают дословно.

**Источник 1 — стоковый LK**, `lk_unpack_v0/lk_a_lk.bin.c:53590-53603`
(символы вида `DAT_ffff0000100268a8` — виртуальный маппинг `0xffff0000_10026000`):

```c
do { } while ((_DAT_ffff0000100268a8 & 0xe) != 0);      // ждать FSM idle
_DAT_ffff000010026884 = param_3 & 0xffff;               // WDATA
_DAT_ffff000010026880 = param_2 & 0xffff | 0x20000000;  // CMD | BIT(29) = запись
...
_DAT_ffff000010026880 = param_2 & 0xffff | param_1 << 0x1d;
do { } while ((_DAT_ffff0000100268a8 & 0xe) != 0xc);    // ждать WFVLDCLR
*param_4 = (short)_DAT_ffff000010026894;                // RDATA, 16 бит
_DAT_ffff0000100268a4 = 1;                              // VLDCLR
```

**Источник 2 — ядро**, `src_linux/linux/drivers/soc/mediatek/mtk-pmic-wrap.c`,
`mt6789_regs[]` (стр. 643) + `pwrap_mt6789` с `.caps = PWRAP_CAP_ARB`.

### Карта регистров

| Регистр | Смещение | Абсолютный адрес | Назначение |
|---|---|---|---|
| `PWRAP_INIT_DONE2` | `0x000` | `0x10026000` | |
| `PWRAP_TIMER_EN` | `0x3E4` | `0x100263e4` | |
| `PWRAP_INT_EN` | `0x450` | `0x10026450` | |
| `PWRAP_WACS2_CMD` | `0x880` | `0x10026880` | команда |
| `PWRAP_SWINF_2_WDATA_31_0` | `0x884` | `0x10026884` | данные записи |
| `PWRAP_SWINF_2_RDATA_31_0` | `0x894` | `0x10026894` | данные чтения (млад. 16 бит) |
| `PWRAP_WACS2_VLDCLR` | `0x8A4` | `0x100268a4` | запись `1` завершает транзакцию |
| `PWRAP_WACS2_RDATA` | `0x8A8` | `0x100268a8` | **статус FSM** |

### Кодирование команды

MT6789 имеет `PWRAP_CAP_ARB` — кодирование **отличается** от legacy-варианта MTK.
Частая ошибка: подставить legacy-формулу `(adr >> 1) << 16`. Здесь адрес идёт **как есть**.

| Операция | Действия |
|---|---|
| Чтение | `CMD = adr` |
| Запись | `WDATA = value`, затем `CMD = adr \| BIT(29)` (`0x20000000`) |

### Состояния FSM (регистр `0x100268a8`)

Маска — `& 0xE`, то есть биты **[3:1]** (`PWRAP_GET_WACS_ARB_FSM(x) = (x >> 1) & 7`):

| `v & 0xE` | Состояние |
|---|---|
| `0x0` | `IDLE` — можно слать команду |
| `0xC` | `WFVLDCLR` — данные готовы, ждёт очистки |

Важно: у legacy-вариантов FSM лежит в битах [18:16] (`>> 16`). Для MT6789 это неверно.

### Готовая последовательность (чтение регистра PMIC)

```
mw.l 0x100268a4 1          # снять возможный подвисший vldclr
md.l 0x100268a8 1          # убедиться: (v & 0xE) == 0
mw.l 0x10026880 <adr>      # команда чтения
md.l 0x100268a8 1          # ждать (v & 0xE) == 0xC
md.l 0x10026894 1          # данные — младшие 16 бит
mw.l 0x100268a4 1          # завершить транзакцию
```

Запись:

```
md.l 0x100268a8 1          # (v & 0xE) == 0
mw.l 0x10026884 <value>
mw.l 0x10026880 <adr | 0x20000000>
```

> Отправлять команды в консоль U-Boot **по одной**. При пакетной отправке нескольких строк
> CDC-ACM консоль теряет символы: наблюдалось превращение `md.l` в `d.l` с ответом
> `Unknown command 'd.l'`. Из-за этого легко принять пропущенное чтение за результат.

## Замеры с железа (2026-08-05, v188)

Все — через `md`/`mw` из шелла U-Boot по USB CDC ACM.

| Что | Адрес | Значение | Толкование |
|---|---|---|---|
| pwrap, начало региона | `0x10026000` (16 слов) | `00008441` во **всех** словах | регистры не различаются |
| pwrap, блок WACS2 | `0x10026880…0x100268a8` | `00008441` | то же значение |
| Запись `0x1234` в WDATA | `0x10026884` | читается `00008441` | запись не фиксируется |
| Соседний регион | `0x10027000` | `00000000` | `0x8441` — **не** дефолт шины |
| infra_ao0 STA (настоящий) | `0x10001090` | `00000000` | PMIC_TMR (бит 0) и PMIC_AP (бит 1) **не заглушены** |
| topckgen CLK_CFG_8 | `0x10000090` | `02010001` | `pwrap_ulposc`: родитель `osc_d10`, гейт (бит 15) снят |
| Контроль чтения MMIO | `0x10000090` и соседи | значения различаются | чтение MMIO в целом исправно |

### Ключевой факт

**Регион pwrap отдаёт константу `0x8441` на любом смещении, а записи не сохраняются.**
При этом соседний адрес `0x10027000` читается как `0x00000000` — значит `0x8441` порождает сам
блок pwrap, а не общий обработчик недоступной памяти.

### Чего делать нельзя

Один раз наблюдался переход `0x100268a8` в `0x0002844d` (то есть `& 0xE == 0xC`, WFVLDCLR) сразу
после записи команды. **Это не воспроизвелось.** Наблюдение получено в пакетной отправке, где
консоль теряла символы. Считать его доказательством работоспособности pwrap нельзя — при повторе
по одной команде статус остаётся `0x8441` без изменений.

## Гипотезы (не проверены)

### A. Регистровый домен pwrap без такта — основная

Шинный интерфейс отвечает (адрес декодируется, отличается от соседей), а регистровый файл стоит
без тактового сигнала — типичная причина «одно слово на все смещения».

Цепочка клоков по `clk-mt6789-infra_ao.c:105-106` и `clk-mt6789-topckgen.c:76,92,697`:

```
CLK_IFRAO_PMIC_TMR (бит 0) ┐
CLK_IFRAO_PMIC_AP  (бит 1) ┘← pwrap_ulposc_ck ← pwrap_ulposc_sel ← osc_d10 ← ulposc
```

Замерами закрыты первые три звена: гейты infra сняты, мультиплексор `PWRAP_ULPOSC_SEL`
(`CLK_CFG_8`, `0x10000090`, биты [10:8] = sel, бит 15 = gate) настроен на `osc_d10` и не заглушен.

Остаётся корневой **`ulposc`**. В дереве `src_linux/linux/drivers/clk/mediatek/` он не описан ни в
одном `clk-mt6789-*.c` (в `clk-mt6789-apmixed.c` упоминаний нет) — то есть поднимается вне
topckgen. Если генератор не запущен, симптом совпадает полностью.

**Следующий шаг:** найти блок управления ULPOSC и проверить, запускает ли его LK.

### B. Аппаратная защита доступа

В живом DT рядом с pwrap есть отдельный узел:

```
pwrap_mpu@10026000 {
        compatible = "mediatek,pwrap_mpu";
        reg = <0x00 0x10026000 0x00 0x1000>;
};
```

MPU может ограничивать доступ по мастеру или по уровню привилегий. LK и U-Boot могут исполняться
на разных exception level — тогда стоковый код имеет доступ, а U-Boot нет. Проверяется чтением
конфигурации MPU и текущего EL.

## MT6366 — регистры для питания SD

Адреса из `src_linux/linux/include/linux/mfd/mt6358/registers.h`, раскладка полей — из
`drivers/regulator/mt6358-regulator.c` (макрос `MT6366_LDO`, стр. 166-188).

| LDO | Роль | Enable (бит 0) | Напряжение | Статус (`qi` = бит 15) |
|---|---|---|---|---|
| **VMCH** | `vmmc` — VDD карты | `0x1CD8` | `0x1E48` | `0x1CE6` |
| **VMC** | `vqmmc` — VccQ шины | `0x1CC4` | `0x1E4C` | `0x1CD2` |

### Кодирование напряжения

Поле диапазона (`vsel_range_mask`) выбирает базовое напряжение, поле `[3:0]` — доводку шагами
по 10 мВ (0…10).

**VMCH** — маска диапазона `0x700` (биты [10:8]), селекторы `{2, 3, 5}`:

| Значение [10:8] | Напряжение |
|---|---|
| `2` | 2.9 В |
| `3` | 3.0 В |
| `5` | 3.3 В |

**VMC** — маска диапазона `0xF00` (биты [11:8]), селекторы `{4, 10, 11, 13}`:

| Значение [11:8] | Напряжение |
|---|---|
| `4` | 1.8 В |
| `10` | 2.9 В |
| `11` | 3.0 В |
| `13` | 3.3 В |

Для обычной SD-карты: VMCH = 3.0 В, VMC = 3.0 В на старте; 1.8 В на VMC нужен только для UHS-I
после переключения сигнальной линии.

### Проверка без записи

Когда доступ к pwrap появится, первым делом прочитать состояние — записи в PMIC делать только
после этого:

```
# VMCH_CON0 — бит 0 = включён ли LDO
mw.l 0x100268a4 1
mw.l 0x10026880 0x1cd8
md.l 0x10026894 1
mw.l 0x100268a4 1

# VMC_CON0
mw.l 0x100268a4 1
mw.l 0x10026880 0x1cc4
md.l 0x10026894 1
mw.l 0x100268a4 1
```

Контрольное чтение — `MT6358_SWCID` (`0xa`): у исправного канала оно обязано отличаться от
значений `CON0`. Если совпадает — данные не идут, транзакция мнимая.

## Состояние поддержки в U-Boot

Драйверов нет вообще:

- `drivers/power/pmic/` — ни одного MTK-драйвера;
- `drivers/power/regulator/` — то же;
- `pwrap` во всём `drivers/` упоминается только в `clk-mt8183.c` и `pinctrl-mt7623.c`, к MT6789
  отношения не имеющих.

Значит любой доступ к PMIC придётся делать сырыми записями (как в `mtk_disp_g99.c`) либо портировать
драйвер целиком.
